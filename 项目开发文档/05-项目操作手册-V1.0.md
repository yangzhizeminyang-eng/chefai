| 项 | 🚀 阶段一 | 📦 阶段二 |

```bash
docker compose --env-file .env.dev up -d postgres redis

```

### 2.2 服务器环境准备

> 📖 **完整命令见 B-D6-1 §2、§3**（腾讯云 CVM 规格、安全组、Docker 安装、镜像加速）。
> 本文档只列**必须确认的三件事**：

| # | 必确认项 | 检查方式 | 不合格后果 |
| --- | --- | --- | --- |
| 1 | 安全组**未开放** 5432 / 6379 | 控制台入站规则 | 数据库暴露公网，高危 |
| 2 | 🔴 **阶段一安全组限来源 IP** | 开放端口仅 22 / 8080，且来源为办公网 IP | 触发备案问题（红线 2） |
| 3 | Docker 日志轮转已配置 | `docker info \| grep -A2 "Registry Mirrors"` + 检查 `/etc/docker/daemon.json` | 系统盘写满 |

### 2.3 配置项速查

| 分组 | 变量 | 是否必须修改 | 说明 |
| --- | --- | --- | --- |
| 基础 | `IMAGE_TAG` | ✅ **禁止 latest** | 回滚唯一前提（B-D6-1 §11） |
| 基础 | `ENV_MODE` | ✅ | `stage1` / `stage2` |
| 数据库 | `POSTGRES_PASSWORD` | ✅ **强密码** | — |
| Redis | `REDIS_PASSWORD` | ✅ **强密码** | — |
| 应用 | `APP_SECRET_KEY` | ✅ **32 位以上随机** | JWT / 字段加密 |
| 应用 | `UPLOAD_TTL_HOURS` | 默认 24 | 🔴 照片 24h 删除（NFR-7.2） |
| 应用 | `RULE_RELOAD_INTERVAL_SEC` | 默认 30 | 风控规则热加载轮询 |
| 模型 | `LLM_API_KEY` | ✅ `【阶段一】` **D1 必须到位** | 阶段一唯一硬前置（Q-06） |
| 模型 | `LLM_MODEL_MAIN` / `LLM_MODEL_LIGHT` | ✅ | 分级调用（成本控制） |

| 阶段二 | `WX_*` | `【阶段二】` | 小程序登录与虚拟支付 |
| 阶段二 | `DOMAIN` | `【阶段二】` | 已备案域名 |

> ⚠️ **配置变更铁律**：任何 `.env` 变更 → **先备份** → 改 → 重启对应服务 → 跑 `smoke-test.sh` → 记录到变更单。

### 2.4 配置变更操作

```bash
cd /opt/ai-cook/deploy

# 5) 记录：变更单编号 / 变更项 / 影响 / 回滚方式
```

### 3.2 本地启动

```bash
# 后端
cd backend
python -m venv .venv && source .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install -r requirements.txt
alembic upgrade head                                   # 迁移
uvicorn app.main:app --reload --port 8000

# 前端（阶段一 Web 演示端 · Vue 3 + Element Plus）
cd web-stage1 && npm install && npm run dev -- --port 5173   # 固定 5173，代理到后端 8000

# 管理后台 · Vue 3 + Element Plus
cd admin-web && npm install && npm run dev -- --port 5174    # 固定 5174，避免与 web-stage1 撞端口
```

**本地端口约定**

| 本地服务 | 端口 | 说明 |
| --- | --- | --- |
| 后端 API | **8000** | `uvicorn`；前端 dev 的代理目标 |
| 阶段一 Web 演示端 | **5173** | Vite dev（显式指定） |
| 管理后台 | **5174** | Vite dev（**必须显式指定**，否则与 5173 冲突后自增，端口不确定） |

**前端构建（产出静态资源）**

```bash
cd web-stage1 && npm ci && npm run build               # 产物 dist/
cd admin-web  && npm ci && npm run build

# 部署到服务器（产物目录由 Nginx 挂载）
rsync -avz dist/ root@<IP>:/opt/ai-cook/web-stage1/
```

| 项 | 说明 |
| --- | --- |
| 构建环境变量 | `VITE_API_BASE=/v1`（同域经 Nginx 反代），**不得硬编码 IP** |
| 按需引入 | Element Plus 走 `unplugin-vue-components` + `unplugin-auto-import`，控制包体积 |
| 深色 / 大字 | 覆盖 Element Plus dark 变量与字号 CSS 变量（PRD §5.5） |
| ⚠️ 小程序 | 阶段二小程序为 **uni-app**，**不可使用 Element Plus**（无 DOM / 浏览器 API），产物由微信开发者工具上传 |

## 4. 部署与发布操作

### 4.1 一键部署

```bash
cd /opt/ai-cook/deploy
cp .env.example .env && chmod 600 .env
vim .env                    # 填密码与 Key（IMAGE_TAG 必须固定）

```

> 📖 完整命令、配置文件全文、FAQ 见 **B-D6-1 §5~§10**。

### 4.2 发布流程

| 步骤 | 操作 | 检查点 |
| --- | --- | --- |
| 1 | 代码合并到发布分支，CI 测试通过 | 风控/硬过滤单测全绿 |
| 2 | 确定版本号 `vX.Y.Z`（语义化：修复/功能/破坏） | 写入 `IMAGE_TAG` |
| 3 | 构建镜像 | `docker compose build api` |
| 4 | 🔴 **发布前安全三验** | ① 一票否决生效 ② 短路返回体无业务字段 ③ 过敏原过滤 = 0 |
| 5 | 打标签归档 | `docker tag` + 推 TCR（可选） |
| 6 | 低峰期切换 | `docker compose up -d --no-deps api` |
| 7 | 冒烟验证 | `bash scripts/smoke-test.sh` |
| 8 | 观察 30 分钟 | 错误率 / P95 / 风控拦截量 / 成本 |
| 9 | 记录发布单 | 版本、时间、变更项、回滚标签 |

> ⚠️ **禁止**：`IMAGE_TAG=latest`、跳过安全三验、在业务高峰期发布。

### 4.3 回滚操作

| 场景 | 操作 | 耗时 |
| --- | --- | --- |
| 应用回滚 | `bash scripts/rollback.sh app v0.9.3` | ~1 分钟 |
| 数据库迁移回滚 | `bash scripts/rollback.sh db <revision>` | 视迁移而定 |
| 配置回滚（开关/规则/权重） | 后台一键切回上一 version（**无需重启**） | 秒级 |
| 灾难恢复 | `bash scripts/rollback.sh restore backups/xxx.sql.gz` | 视数据量 |

> 🔴 破坏性数据库变更**无法无损回滚**，只能恢复备份 —— 因此**发布前必须先备份**。

### 4.4 四个远程开关操作（§11.8 强制）

**操作入口**：后台 →「远程开关」

| 开关 | 关闭后用户表现 | 什么时候用 |
| --- | --- | --- |
| `switch.recommend` | 推荐入口置灰 + 说明「推荐功能维护中」 | 推荐链路故障 / 成本熔断 |
| `switch.vision` | 拍照入口置灰 + 引导手选 | 多模态服务异常 |
| `switch.qa` | 搜索退化为菜名/食材名精确匹配 | 自由问答异常或幻觉风险 |
| `switch.payment` | 会员入口隐藏（已购权益可查看） | 支付故障 / 合规调整 |

| # | 操作规则 |
| --- | --- |
| 1 | 开关**即时生效**（前端 60s 内拉取，`SWITCH_CACHE_TTL_SEC`） |

### 6.1 规则库结构

## 8. 日常运维操作（SOP）

### 8.1 每日巡检清单（⭐ 建议 10 分钟完成）

| # | 检查项 | 命令 | 通过标准 |
| --- | --- | --- | --- |
| 1 | 容器状态 | `docker compose ps` | 4 容器 Up(healthy) |
| 2 | 磁盘 | `df -h /` | 使用率 < 80% |
| 3 | 内存 | `free -h` | 可用 > 20% |
| 4 | 错误率 | `docker compose logs --since 24h api \| grep -c "ERROR"` | 无异常增长 |
| 5 | 推荐 P95 | §13.1 SQL | ≤ 6s |
| 6 | **风控拦截量** | §13.1 SQL | 非 0、非异常突增 |
| 7 | `safe_mode` 触发 | `grep -c safe_mode` 日志 | 无或极少 |
| 8 | 今日成本 | §13.1 SQL | 在预算水位内 |
| 9 | 备份完成 | `ls -lh backups/ \| tail -3` | 有当日备份 |
| 10 | 照片清理 | `ls /opt/ai-cook/data/uploads \| wc -l` | 无 24h 以上文件 |

**一键巡检脚本（建议加到 crontab 每日 09:00）**

```bash
#!/usr/bin/env bash
# deploy/scripts/daily-check.sh
cd /opt/ai-cook/deploy
echo "===== $(date '+%F %T') 每日巡检 ====="
docker compose ps
df -h / | tail -1
free -h | head -2
docker compose exec -T postgres psql -U aicook -d aicook -c "
  SELECT 'today_blocked' AS item, count(*)::text AS v FROM risk_log
    WHERE created_at >= CURRENT_DATE AND action='blocked'
  UNION ALL SELECT 'today_cost_cents', ROUND(COALESCE(SUM(cost_cents),0),2)::text
    FROM agent_trace WHERE created_at >= CURRENT_DATE
  UNION ALL SELECT 'p95_recommend_ms', COALESCE(ROUND(PERCENTILE_CONT(0.95)
      WITHIN GROUP (ORDER BY duration_ms))::text,'-')
    FROM agent_trace WHERE created_at >= CURRENT_DATE;"
echo "===== 巡检结束 ====="
```

## 9. 关键业务流程操作指引（跨角色）

### 9.1 「推荐结果不准」排查流程

```
① 取 request_id（用户反馈可带）
② 查 trace：GET /v1/trace/{request_id} → 看各节点耗时与状态
③ 查被过滤原因：filtered_by 计数（过敏原/忌口/难度）
④ 查排序因子：results[].rank_reasons 是否符合预期
⑤ 定位：
   ├ 过滤过多   → 检查档案过敏原/忌口是否登记过宽
   ├ 排序异常   → 检查 rank.weights 配置与历史偏好数据
   └ 召回为空   → 检查向量索引与菜谱发布状态
⑥ 处置：调权重（走 remote_config，留操作日志）或补菜谱
```

### 9.2 「风控误报 / 漏报」处理流程

| 类型 | 处置 |
| --- | --- |
| **误报** | 用户申诉 → 后台复核 → 收窄触发条件（§6.2）→ 灰度验证 |
| **漏报** ⚠️ | **立即上报**（甲方产品 + 专家）→ 24h 内加规则（§6.5）→ 复盘边界用例 → 补入测试集 |
| 漏报复盘要求 | 补充到食品安全高危样本集，并回补自动化测试用例 |

### 9.3 「识别不准」处理流程

```
① 查识别纠正率埋点（ingredient_recognize_correct）
② 若整体 < 90% Top-3 或纠正率 > 15%：
   ├ 检查图片压缩是否过度（前端压缩参数）
   ├ 检查视觉模型档位与 Prompt
   └ 检查食材库是否缺条目（用户改了但库里没有）
③ 处置：补食材条目 / 调压缩参数 / 换模型档位
④ 若单图问题 → 引导用户手动更正（已是产品内能力）
```

### 9.4 「成本超预算」处置流程

```
① 看板定位：按功能维度找大头（预期推荐约 70%）
      ↓
② 依次启用降本手段（B-D3 §12.2）：
   推荐缓存 → RAG Top-K 收窄(20→8) → 指令类走轻模型 → TTS 缓存
      ↓
③ 仍超预算 → 80% 告警 / 100% 熔断（可配置关闭自由问答或推荐）
```

### 9.5 「服务不可用」应急流程

| 步骤 | 操作 | 责任 |
| --- | --- | --- |
| 1 | 确认范围：`docker compose ps` + `curl /v1/healthz` | 运维 |
| 2 | 按 B-D6-1 §10 排查（日志 → 原因 → 处置） | 运维 |
| 3 | 短时间无法修复 → **远程开关降级**（关推荐/识别/问答） | 运维 + PM |
| 4 | 影响面大 → **回滚上一版本**（`rollback.sh app <tag>`） | 运维 |
| 5 | 恢复后跑 `smoke-test.sh`，全绿才算恢复 | 运维 |
| 6 | 事后复盘，记录到遗留问题清单 | PM |

> 🔴 **绝不接受的处置**：**风控不可用时直连模型**。风控异常只能进保守模式（RL-4）。

### 9.6 「安全事件」应急流程（含应急下架开关）⭐

```
【触发】用户照做后不适 / 媒体报道食品安全事件 / 监管通报
   ↓
① 立即暂停相关内容：菜谱下架 + 规则灰度/全量开启（§6.5）
   ↓
② 保全证据：导出 risk_log + agent_trace + 会话记录（request_id 全链可追溯）
   ↓
③ 通知：甲方产品 + 法务 + 专家（30 分钟内）
   ↓
④ 评估是否需**启动应急下架开关**（关推荐模块 = 全局止血）
   ↓
⑤ 修复：补规则 / 下架菜谱 / 更新话术
   ↓
⑥ 复盘：写入遗留问题清单，回补测试集
```

```sql
SELECT node_name, count(*), ROUND(PERCENTILE_CONT(0.95)
       WITHIN GROUP (ORDER BY duration_ms)) AS p95_ms

GROUP BY 1 ORDER BY p95_ms DESC;
```

### 12.5 术语表

| 术语 | 定义 |
| --- | --- |
| **一票否决（Veto）** | 风控命中时**控制流短路**，其余业务节点**不执行**（非「执行后丢弃」） |
| **布尔硬过滤** | 不满足条件的内容**完全不出现在结果中**，与「降权」严格区分 |
| **双重风控** | 输入侧扫「用户问了什么」+ 输出侧复核「系统准备回答什么」 |
| **保守模式** | 风控不可用时的降级态：禁止高风险推荐 + 明确告知，**绝不直连模型** |
| **远程开关** | 不重新发版即可独立下线某模块（推荐/识别/问答/支付） |
| **断点续做** | 烹饪中途退出后可从上次步骤继续 |
| **PoC** | 概念验证，本项目阶段一即 PoC |
| **三档匹配** | 「现在就能做」「差 1–2 样」「需要多买几样」 |

## 一、一句话定位

**产品里的"智能体"不是一个聊天机器人，而是一张有 22 个节点的受控编排图。**
它扮演的是一支**流水线班组**：1 个只负责分派活的调度员、4 个只按规章办事的门卫、若干组干具体活的工人，以及 3 个统一收口的出口。**全图只有 3 个图节点真的调用大模型。**

| 数字 | 值 |
| --- | --- |
| 主图节点 | 13（注册于 `AGENT_REGISTRY`） |
| 子图内部节点 | 9（推荐子图 5 + 创新子图 4） |
| 节点总数 | 22 |
| GPU/大模型参与节点 | **3**（supervisor / node_free_qa / innovation_generate）+ ability 层 2 处（营养估算、图像识别） |
| 终止出口 | 3（finalize 正常收口 / emit_safety_response 一票否决 / safe_mode_handler 保守模式） |
| 风控规则 | 24 条 DB 规则（FS 11 / MR 4 / OB 5 / PS 2 / SP 2）+ 1 条内置注入拦截 |
| 远程开关 | 5 个（recommend / vision / qa / payment / innovation） |

## 二、四类角色

### 角色 1：调度员 —— supervisor（唯一的 LLM 决策节点）

| 项 | 内容 |
| --- | --- |
| 形态 | llm（timeout 3000ms） |
| 做了什么 | 把用户输入（文本 + 已选食材）分类成 **10 类意图**：`recommend_by_ingredients` / `search_recipe` / `photo_recognize` / `free_qa` / `cooking_help` / `nutrition_query` / `inventory_op` / `smalltalk_or_out_of_scope` / `composite_recommend_nutrition` / `innovation` |
| 关键约束 | **LLM 只识别意图，不决定调用哪个节点**。意图 → 节点由代码字典 `INTENT_ROUTES` 查表得到。LLM 说什么都无法改变调用路径 → 路由可枚举、可测试、无法被 Prompt 注入改写 |
| 降级 | LLM 不可用 / JSON 解析失败 → 关键词兜底分类（确定性、可枚举），trace 记 `degraded` |
| 双保险 | 若入口闸门已写入一票否决标记，节点立即以 `skipped_by_veto` 返回，不执行任何业务逻辑 |

### 角色 2：门卫 —— 风控守卫层（4 节点，纯规则，不调大模型）

| 节点 | 超时 | 做了什么 |
| --- | --- | --- |
| `intake_guard` | 500ms | 扫描「用户输入文本 + 食材名」（食材名本身也可能是高危载体，如"发芽土豆"）→ 命中即一票否决；扫描异常/超时 → `UNKNOWN` → 保守模式 |
| `output_guard` | 500ms | 扫描「全部菜名 + 推荐理由 + 问答文本」；DB 输出规则命中即整体阻断；敏感词二级替换对问答文本生效 |
| `emit_safety_response` | 500ms | 一票否决出口。组装 blocked 响应（**绝不含 results/candidates/nutrition**），为未执行的业务节点补 `not_executed` 取证 span，落 `risk_log` |
| `safe_mode_handler` | 500ms | 保守模式出口。TXT-G06 固定话术 + partial 说明，**绝不在风控不可用时直连模型** |

**底层引擎** `RiskEngine`（`app/safety/engine.py`）：24 条规则存于 `risk_rule` 表，进程内存缓存 + 指纹校验，指纹变化即热重载（不引入 Redis）；支持关键词包含 / 分组组合 / 正则三类匹配，全部大小写不敏感；按 `critical > high > medium` 降序遍历，首个命中即返回；`scan()` 整体 try/except 全包裹，任何异常返回 `UNKNOWN_VERDICT`（**绝不抛出、绝不放过**）。另有内置内存规则拦截 Prompt 注入（忽略指令 / 无视规则等中英文越狱话术）。

**为什么门卫不用大模型**：确定性、可审计、零成本、毫秒级、**没有 Prompt 注入攻击面**。这是整套安全设计的地基。

### 角色 3：工人 —— 业务执行层

**3-1 推荐子图（5 节点，包装为一个主图节点 `subgraph_recommend`，超时 5000ms）**

```
assemble_context → recipe_retrieve → hard_filter → ( recipe_rank ∥ node_nutrition ) → END
```

| 节点 | 做了什么 |
| --- | --- |
| `assemble_context` | 把食材名称/别名/ID 解析成 `ingredient_id`；文本无显式食材时从输入文本确定性匹配 |
| `recipe_retrieve` | 混合召回：食材覆盖数降序 + 菜名 ILIKE/别名匹配 |
| `hard_filter` | **布尔硬过滤（DB 层 WHERE，非打分、非降权）**：过敏原命中即排除、忌口命中即排除、难度超上限即排除、设备差集非空即排除。输出 `filtered_by` 计数作为"过滤而非降权"的验收证据 |
| `recipe_rank` | 7 因子加权（覆盖 0.30 / 临期 0.15 / 口味 0.15 / 目标 0.15 / 难度 0.10 / 历史 0.10 / 热度 0.05）+ 生成 `rank_reasons` 推荐理由 + 三档 `match_level`，取 Top 8 |
| `node_nutrition` | 营养估算，**与 `recipe_rank` 并行执行**（hard_filter 后 fan-out 两条边，同一 superstep 并行） |

> 并行节点的 trace 依赖 `CookingState.trace` 上的 `Annotated[list, operator.add]` reducer 正确合并——这是「Agent 调度可视化面板」的数据基础。子图使用独立 schema（`sub_trace`）以**避免 span 重复累加**（已实测踩坑并修复）。

**3-2 专用节点（4 个，全部规则/查表，不调大模型）**

| 节点 | 超时 | 做了什么 |
| --- | --- | --- |
| `node_free_qa` | 5000ms | 唯一调 LLM 的业务节点。受限问答：≤5 句 + 合规约束 + 失败兜底固定话术 |
| `node_inventory_op` | 1000ms | 库存查询：查在库 5 条 + 临期 3 条，模板应答 |
| `node_nutrition_query` | 1000ms | 营养查询：查 `meal_record` 今日汇总，模板应答 |
| `node_cooking_help` | 1000ms | 烹饪求助：查进行中会话进度，模板应答 |

**3-3 创新子图（4 节点，入口 `node_innovation_entry`，超时 8000ms）**

```
innovation_precheck → innovation_property_match → innovation_pairing_check → innovation_generate → END
```

| 节点 | 做了什么 |
| --- | --- |
| `innovation_precheck` | 🔴 安全前置：复用 `run_precheck_core`——高危闸门 / 过敏原直接拒绝 / 特殊人群 / taboo 查表，任一命中即置 `blocked`，**后续节点短路** |
| `innovation_property_match` | 食材五属性匹配（质地 / 水分 / 风味 / 耐热 / 吸油等可观察烹饪科学属性） |
| `innovation_pairing_check` | 🔴 搭配规则查表（**结论必须查表**）：`taboo` → 直接拒绝；`conflict` → 记入依据要求生成时避开；`recommend` → 正向依据。技法建议仅在白名单内才透出 |
| `innovation_generate` | 受约束生成：配料由配比模板量化（300g/150ml 级别，无"适量/少许"），**LLM 只负责表达** |

### 角色 4：收口 —— compose + finalize（2 节点，纯规则）

| 节点 | 超时 | 做了什么 |
| --- | --- | --- |
| `compose` | 1000ms | 三档结果组装 + **免责声明附着** + 降级标注 + 复合意图标注 |
| `finalize` | 1000ms | trace 落库 `agent_trace` + 最终响应组装 |

## 三、一次推荐请求里，智能体做了什么事（实测 trace）

以「选土豆/青椒/猪五花肉 → 去推荐」为例，调度面板可见 **11 个节点 span**（总耗时 1030ms / 298 token / ¥0.0008）：

```
intake_guard（放行）
  → supervisor（deepseek-flash 识别意图 = recommend_by_ingredients，268/30 token，¥0.0008）
    → assemble_context（解析食材 ID）
      → recipe_retrieve（召回候选）
        → hard_filter（过敏原/忌口/难度/设备布尔过滤）
          → recipe_rank（7 因子排序）∥ node_nutrition（营养估算，并行）
        → subgraph_recommend（子图收口）
  → compose（三档组装 + 免责附着）
    → output_guard（输出扫描，正常放行）
      → finalize（trace 落库 + 响应）
```

**若输入的是一票否决类问题**（如"木耳泡一晚上明天炒行吗"）：
```
intake_guard → 命中 FS-001 → emit_safety_response（直达 END）
```
`supervisor`、`assemble_context`、`recipe_retrieve`、`hard_filter`、`recipe_rank`、`node_nutrition`、`compose` **全部不执行**，trace 中补标 `not_executed` 作为取证——这就是"一票否决 = 控制流短路"而非"标记后丢弃"的直接证据。

## 四、让这套编排成立的关键设计取舍

| # | 取舍 | 理由 |
| --- | --- | --- |
| 1 | **LLM 最小化**：22 个节点只有 3 个用模型 | 成本、延迟、确定性、合规面全面收敛 |
| 2 | **LLM 只识别意图，路由查字典** | 路由可枚举、可测试；Prompt 注入无法改写调用路径 |
| 3 | **风控零 LLM** | 无注入面、毫秒级、零成本、可审计 |
| 4 | **一票否决 = 条件边短路** | 业务节点根本没执行，而不是执行完再丢弃 |
| 5 | **双闸门**：输入侧 + 输出侧 | 分别拦截"危险提问"与"危险输出"，都不可省 |
| 6 | **过敏原 = 布尔硬过滤** | 独立节点，位于检索与排序之间，DB 层 WHERE；`filtered_by` 计数即验收证据 |
| 7 | **风控异常 → 保守模式** | `status == UNKNOWN` 一律不直连模型，宁可不答 |
| 8 | **可插拔注册表** | `AGENT_REGISTRY` + `register()`；新增 Agent 只注册，不改 `main_graph` 装配逻辑 |
| 9 | **并行 + trace reducer** | `hard_filter` fan-out 到排序与营养；`operator.add` 合并 span，支撑调度面板 |
| 10 | **脱敏** | state 只存 `user_id_hash`（sha256 前 12 位） |
| 11 | **子图 schema 隔离** | 子图用 `sub_trace` 独立通道，防止经主图 reducer 重复累加 |
| 12 | **运行期可调** | 5 个模块级远程开关 + 7 因子权重均可远程配置（60s 生效） |

## 五、智能体的"可观测性"产出

每个节点执行后写入一条 trace span，字段与 `agent_trace` 表列一一对应：

`node_name` / `status`（ok / degraded / failed / timeout / not_executed / skipped_by_veto）/ `duration_ms` / `model_name` / `prompt_tokens` / `completion_tokens` / `cost_cents` / `rule_hit`

三类 span 状态是这套设计的特色取证手段：
- `not_executed` —— 业务节点因一票否决**从未执行**（入口否决场景）
- `skipped_by_veto` —— 因双保险标记**主动跳过**（supervisor / finalize）
- `degraded` —— LLM 不可用走了兜底（如 supervisor 关键词兜底）

## 六、术语对齐（避免与甲方口径混淆）

| 甲方口径 | 本项目实现 | 关系 |
| --- | --- | --- |
| Agent / 智能体 | LangGraph 图节点（22 个） | 一个节点 = 一个 Agent 职责单元 |
| 多智能体架构 | 主图 + 2 个子图的编排 | 不是多个独立 LLM 互相聊天 |
| 风控 Agent | 4 个规则节点 + RiskEngine | **不调大模型** |
| 一票否决 | `route_after_intake_guard` 条件边短路 | 控制流层面，非标记层面 |
| Agent 调度可视化 | `agent_trace` 表 + `/trace` 页面 | 消费 trace reducer 合并后的 span |

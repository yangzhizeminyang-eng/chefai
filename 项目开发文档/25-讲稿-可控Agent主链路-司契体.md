## 第三块 · 可控的 Agent 主链路

**它要解决的问题是：模型可以帮忙理解请求，但不能偷偷决定系统下一步做什么。**

技术栈上编排用 LangGraph，图状态是显式的；模型走 Provider 抽象，可以一键回退到 mock，服务始终能启动；排序权重这类规则存在 remote_config 表里，不重新发版就能调。

实现了把一次请求做成一张固定拓扑的图：入口先过闸门，再交给 supervisor。supervisor 是主图里唯一调大模型的节点，而且它只输出一个意图标签，不回答问题、也不选分支；走到哪个节点，由代码里的 INTENT_ROUTES 字典决定，10 类意图可枚举、可测，没命中字典的兜底到受限问答。所有正常路径都必须汇到 compose 和出口闸门才能返回。

达到了整个主图只有三个终止节点、其余没有任何一条直达 END 的路径的效果，而且这一条是用代码遍历编译后的图验证出来的，不靠人看图，18 条图结构测试全绿。问答路径上模型可以按需调用工具，但最多 3 轮、总预算 25 秒，失败或解析不出来就当作完成、正常收敛，不往编排层抛异常——**模型掉线，链路退化，但不会崩**。

可回放这块，节点耗时、风控判定和命中规则 ID、哪些节点被跳过，全部写进 trace，按 request_id 能查回来；被否决的那次，业务节点会整排标成 not_executed。所以这条链路既能跑通"选食材—拿推荐—看详情—开始烹饪"，也能事后回答"为什么给了这个结果、为什么这次被拦"。

边界我也说清楚：安全节点短路、候选过滤、用户数据隔离都有自动化测试覆盖，但**中断恢复没做**。阶段一是单轮请求，没有人工介入的需求，所以没上 checkpointer；创新菜这类长任务走的是独立的异步任务表和启动恢复，不是图上的 checkpoint。这条算阶段二再做。

顺带一个我自己踩的坑：想在业务节点清单里追加创新入口，写法是对模块命名空间重新绑定，结果 Python 的 import 是值拷贝，common 模块里的清单根本没变，实测证据是否决 trace 里漏掉了这个节点。改动量极小，但直接影响取证链的完整性——这类问题靠自检发现并登记成风险，比等用户撞上强。

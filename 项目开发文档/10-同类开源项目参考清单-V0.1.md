## 一、A 类：本体最像的成熟产品（可直接对标领域模型与工程结构）

| 项目 | 星级 | 技术栈 | 许可证 | 与本项目对应的模块 |
| --- | --- | --- | --- | --- |
| **[Mealie](https://github.com/mealie-recipes/mealie)** | 13,513★ | Python 后端 + Vue 前端 | **AGPL-3.0** | 菜谱、膳食计划、购物清单、REST API。**与你的技术栈最同构** |
| **[Grocy](https://github.com/grocy/grocy)** | 9,582★ | PHP | MIT | 「冰箱之外的 ERP」：库存、**到期日管理**、购物清单、设备/家务 |
| **[Tandoor Recipes](https://github.com/TandoorRecipes/recipes)** | 8,661★ | Python(Django) + HTML | GitHub 未识别，**须核对** | 菜谱、膳食计划、购物清单、**食材解析与份数缩放** |
| **[KitchenOwl](https://github.com/TomBursch/kitchenowl)** | 3,737★ | Flutter + Flask | **AGPL-3.0** | 购物清单 + 菜谱；2026-03 起提供 **MCP 工具**管理家庭库存 |

**为什么值得读**

- **Mealie**：唯一与你的栈（Python 后端 + Vue 前端）同构的成熟项目，建议作为**接口契约设计 + 前端工程结构**的第一参照，直接对照你的 B-D6 接口文档。
- **Grocy**：库存/到期日/购物清单的领域模型最完整，对应你的 P-22~P-24；它的"用户自填到期日但不判定可食性"边界处理，与你的 RL-3 口径可以互校。
- **Tandoor**：**食材解析（把"2 根中等大小的胡萝卜"拆成数量+单位+食材）与份数缩放算法**最值得读，对应你的份数缩放与「克/毫升/勺」计量单位实现。
- **KitchenOwl**：可作为"厨房域如何暴露 MCP 工具给 AI 调用"的样本。

## 六、许可证风险提示（⚠️ 本条最重要）

本项目「数据资质」类红线明确要求开源许可证合规，因此**必须先分类再决定怎么用**：

| 许可证 | 涉及项目 | 风险与义务 |
| --- | --- | --- |
| **AGPL-3.0** | Mealie、KitchenOwl、openfoodfacts-server | **网络服务传染性**：若把 AGPL 代码并入后端并以网络服务对外提供，你的修改版也须以 AGPL 开源。**只读设计不复制代码**没有义务；一旦复制代码即触发 |
| **ODbL（数据许可）** | Open Food Facts 的**数据库** | 署名义务 + **衍生数据库需同源开放**。整体搬运进自己的知识库而不开放存在合规风险，须先核对官方许可页 |
| **MIT / Apache-2.0** | Grocy、recipe-scrapers、openfoodfacts-python、LangGraph、guardrails、NeMo-Guardrails、food-recognition、im2recipe | 商用友好，保留许可证与版权声明即可 |
| **Unlicense** | HowToCook | 公共领域，最宽松（本项目已使用其语料，风险最低） |
| **未识别 / 无 LICENSE** | Tandoor Recipes（GitHub 未识别）、Murgio/Food-Recipe-CNN（无） | **无 LICENSE 默认"保留所有权利"，禁止复用代码与权重**；Tandoor 需先核对仓库 `LICENSE` 文件 |

## 七、对照结论：哪些能抄、哪些是你的差异化

### 可以大胆对照的（领域层）

| 你的模块 | 最佳参照 |
| --- | --- |
| 菜谱/食材/别名/单位换算的数据表设计（28~32 张表） | Mealie + Tandoor + Grocy |
| 库存、到期日、购物清单（P-22~P-24） | **Grocy**（最完整） |
| 份数缩放、食材解析、「克/毫升/勺」计量 | **Tandoor** |
| 菜谱字段口径与来源标注 | recipe-scrapers（schema.org/Recipe） |
| 过敏原分类体系 | Open Food Facts `allergens_tags` ↔ GB 7718 八大致敏原 |
| 后端接口契约与 Vue 前端工程结构 | **Mealie**（栈同构） |

### 没有现成对标物的（你的差异化，答辩时可直接讲）

上述**所有**项目——包括四家成熟产品——都停留在「结构化 CRUD + 规则引擎」的做法，**没有任何一家实现了**：

1. **多智能体编排**（22 节点主图 + 子图，含并行 fan-out）
2. **输入/输出双闸门风控**，且风控**刻意零 LLM**
3. **一票否决 = 控制流短路**（业务节点根本不执行，trace 补 `not_executed` 取证）
4. **过敏原布尔硬过滤**（DB 层 `WHERE`，非降权，`filtered_by` 计数作为验收证据）
5. **风控 UNKNOWN → 保守模式**（宁可不答，绝不直连模型）
6. **AI 创新菜谱的用户私有向量分区**（`source='ai_private'` + `owner_user_id`）
7. **面向合规的 Agent 调度可视化**（token/成本/命中规则全量可追溯）

> 面试/答辩口径建议：**领域模型向成熟项目学，控制流与安全设计讲自己的原创取舍**。

## 八、建议的阅读顺序（性价比排序）

1. **Mealie** —— 接口契约 + Vue 工程结构（半天）
2. **Grocy** —— 库存/到期/购物清单领域模型（半天）
3. **Tandoor** —— 食材解析与份数缩放算法（2 小时）
4. **recipe-scrapers** —— 菜谱规范化字段清单（1 小时）
5. **Open Food Facts** —— `allergens_tags` 分类法对照（1 小时）
6. **NeMo-Guardrails / guardrails-ai** —— 护栏规则的工程化组织方式（2 小时）
7. **D 类同题 Agent** —— 只看功能覆盖面与 trace 设计，**不抄代码**（1 小时）
